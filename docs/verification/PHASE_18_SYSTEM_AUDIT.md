## 0. How to read this document

Every material claim is labelled with one of the following evidence classes:

| Label | Meaning |
|---|---|
| **Observed** | Directly returned by a running endpoint, read from the database, or read from source code during this audit. |
| **Derived** | Computed by this audit from observed values (sums, ratios, counts). |
| **Model** | Output of a model or deterministic engine operating on real inputs. |
| **Simulation** | Generated without a real input observation (RNG, seeds, fabricated bands, constant forcing). |
| **Recommendation** | Audit judgement about what should change. |

A feature is **not** considered verified because code exists. It is verified only when a runtime request, database query, test, or browser render produced the claimed behaviour during this audit.

The audit deliberately separates three questions that the project's documentation currently conflates:

1. **Does the software run?**
2. **Does the feature do what its name says?**
3. **Is the output scientifically valid or operationally usable?**

OceanAI currently answers "yes" to (1) for most routes, "partly" to (2), and "no" to (3) for most of the marine intelligence chain.

## 1. Executive summary

OceanAI is two products in one repository.

### 1.1 The India water-intelligence product is real and is the strongest part of the system

- **4,601,153** water-quality observations are stored in PostGIS.
- **2,740** water bodies, **4,951** monitoring stations, **35** states and **613** districts are represented.
- `GET /api/v1/water-overview` returns the real counts in **160–332 ms** (857 ms first cold call).
- `POST /api/v1/water/ask` answers a Mithi River question in **~2.1 s**, with `status="grounded"`, citations, and explicit limitations, and **`llm_used=false`**. It is a deterministic retrieval pipeline, not an LLM wrapper.
- The India map, Ocean Map, candidate review, events, health and models pages were visually verified in a real browser. The `/app/ai` and `/app/map` routes return HTTP 200; other water detail routes were not individually exercised.
- Most water bodies are honestly reported as `NO_RECENT_DATA` (2,722 of 2,740 have no recent data), which is the correct behaviour for a sparse monitoring archive.

This subsystem is demo-ready **with caveats**: upstream CPCB/NWDP provenance was not re-verified in this audit, 2,722 bodies have no recent data, and some strings contain mojibake (`A�`).

### 1.2 The marine "intelligence" chain is mostly a synthetic demonstrator presented with operational language

The marine chain (SAR full-scene, optical evidence, fusion, AIS, drift, impact) runs end to end, but the substance is largely fabricated or hardcoded:

- Full-scene SAR never reads a raster. It injects 3–6 random "dark formations" with `numpy.random` (`sar_scene_processor.py:181-229`).
- Optical "BOA reflectance" bands are generated by RNG (`cog_extractor.py:51-138`); no COG is read. All eight sampled candidate image endpoints and the optical product endpoint return **404**.
- Fusion returns a hardcoded **0.92** concordance and the sentence **"High probability petroleum slick"** (`multi_sensor.py:312-319`) from those simulated inputs.
- AIS vessels and tracks are seeded around the candidate coordinates (`seed_vessels.py:92-226`), then the engine "discovers" a 0.99 association it was constructed to find.
- Drift uses a constant 0.22 m/s / 90° current, no CMEMS, no bathymetry, no coastline; beaching is a random draw conditioned only on an `is_coastal` boolean (`lagrangian_drift.py:237-250`).
- Impact uses 9 hardcoded lat/lon points, not PostGIS geometries (`environmental_impact_screener.py:28-120`); the real candidate `cand_s1_0036` returns **0 proximate receptors / LOW**.
- The candidate review UI exposes `split` and raw SAFE scene IDs, and the API returns them, so the claimed "blind" benchmark review is not blind.

### 1.4 If only five things are fixed first

1. **Remove research ground truth from public surfaces.** `split` and `safe_scene` are returned by `/api/v1/sar-candidates` and displayed in `CandidateReview.tsx:284-297`. This invalidates the blinding and held-out benchmark claims.
2. **Stop presenting simulation as observation.** Add mandatory provenance and UI "SIMULATED" banners; remove "High probability petroleum slick" and "Primary Suspect" until the underlying inputs are real and validated.
3. **Make GET endpoints read-only.** They currently seed candidates, process scenes, run drift simulations, correlate vessels, and evaluate impacts. The audit itself accidentally inserted `sim_53e90590af26` and wrote scene files by issuing GETs.
4. **Quarantine test fixtures.** Six `cand_test_*` rows and 8 seeded reviews are counted in the operational 306-candidate KPI and shown in the analyst queue.
5. **Fix the CWD-relative data paths.** All eight sampled candidate image endpoints return 404, the optical product endpoint returns 404, and 7 of the 9 failing tests fail for the same reason.

## 2. Audit scope, method, and limitations

### 2.1 Method

|---|---|

### 2.2 What this audit did **not** verify

- **PostGIS integration test:** `tests/test_postgis.py` was intentionally excluded (`--ignore`). The running PostGIS instance was inspected directly instead.
- **Docker backend image:** the backend was run natively with uvicorn. The Compose backend image was not built or started.
- **Agents / reports / LLM providers:** the agent workflow and Gemini/OpenAI/Anthropic adapters were not exercised. Their documentation is detailed, but this audit makes no claim about them.
- **External providers:** CDSE credentials, live ERA5/CDS, CMEMS, satellite AIS and Bhuvan were not configured. Any capability that requires them is **unverified/unavailable**, not "working".
- **Upstream water provenance:** the 4.6M observations were counted and queried, but the original CPCB/NWDP download and transformation were not re-run.
- **Responsive browser matrix:** screenshots were taken at a desktop viewport; no tablet/mobile matrix was run.
- **Load/soak testing:** only short repeated latency probes were performed.

### 2.3 Safety constraints honoured

- No `docker compose down -v`, volume prune, `git reset --hard`, `git clean -fd`, `DROP`, or table recreation.
- The existing PostGIS container was restarted, not recreated.
- No application code was modified.
- No secret values are reproduced in this document.
- Two audit side effects are disclosed in Appendix C and were deliberately **not** deleted.

### 4.4 The central provenance defect

`GET /api/v1/sar-candidates` returns:

```json
{
  "source": "sar_candidates:v2.2_era5",
  "contains_simulated_data": false,
  "evidence_levels": ["DETECTED"]
}
```

This is **false for the downstream chain**. The candidate rows themselves are model outputs from a real research CSV, so "DETECTED" is defensible for the row. But the same page and API surface also serve:

- synthetic full-scene footprints,
- synthetic optical metrics,
- seeded AIS associations,
- constant-forcing drift,
- static-receptor impacts.

None of those carry a `SIMULATED` marker. `contains_simulated_data` is constructed by `make_provenance` from a hand-written `{"is_simulated": False}` record in `candidates.py:114-118`, not computed from the evidence. This is the single most important provenance failure in the system.

### 5.3 SAR candidate review — useful plumbing, broken blinding

**What exists**

- `backend/app/services/candidate_service.py` seeds 300 rows from `data/models/sar/v2_2_scene_clean/phase13_1_per_sample_audit.csv` and creates 6 test fixtures.
- `backend/app/api/routes/candidates.py` exposes list, summary, map points, detail, review submission, image, optical, fusion, vessels, drift and impact.
- `frontend/src/pages/CandidateReview.tsx` renders the list, detail, wind context, review actions, fusion panel, vessel cards and drift/impact panels.

**What works**

- 306 candidates are listed and filtered.
- Summary KPIs reconcile to 306 total (207 eligible + 99 background).
- Review submission persists a row and updates candidate review status.
- Foreign keys and indexes are intact; 0 orphan reviews.
- Detail, summary, list and fusion responses are fast (9–26 ms).
- All 306 confidences are correctly marked uncalibrated.

**What is broken**

1. **Ground-truth leakage (P0).** `SARCandidateOut` includes `split` and `safe_scene` (`schemas/candidate.py:20-22`), even though its docstring claims "research ground truth codes ... are omitted to prevent reviewer bias" (`:11-16`). Live response for `cand_s1_0036`:
   - `split = "Benchmark 1 (Phase 12 Held-Out Test Set)"`
   - `safe_scene = "S1A_IW_GRDH_1SDV_20190801T160520_20190801T160545_028378_0334F0_B580.SAFE"`
   The UI displays both (`CandidateReview.tsx:284`, `:293-297`), including the literal string "(Research Benchmark)".
2. **Candidate images are 404 (P1).** `DATA_DIR = Path("data/training/sar_oil_v2")` and `IMAGES_DIR = DATA_DIR / "images"` are CWD-relative (`candidate_service.py:25-26`). With the backend started from `backend/`, they resolve to `backend/data/...`, which contains **0** images; the repository root contains **881**. All eight sampled candidates, including `cand_s1_0036`, returned 404. The same defect causes the candidate image test failure.
3. **Reads seed writes (P0).** `list_sar_candidates` calls `seed_candidates_from_audit` (`candidates.py:93-94`); detail does the same (`:158`); summary and map points do it in the service (`candidate_service.py:270`, `:531`). A GET can insert 300 rows.
4. **Test fixtures in the operational queue (P0).** Six `cand_test_*` rows are present with `split="test_acceptance_phase13_3"` and fake `_TEST` SAFE IDs. `cand_test_standard_001` is first in the default list. They are included in the 306 total and in the review KPIs.
5. **Seeded reviews (P0).** 8 reviews exist from 7 role-style reviewer IDs (`lead_analyst_test`, `analyst_phase13_4`, `environmental_officer`, etc.). Notes read "Analyst Decision 1...", "Analyst Decision 2...". Five candidates are marked reviewed (4 fixtures + `cand_s1_0036`). These are demo artefacts, not real analyst decisions.
6. **Review identity is self-reported (P2).** `CandidateReviewCreateIn.reviewer_id` defaults to `"analyst_local"` (`schemas/candidate.py:97-100`). OpenAPI has **no** security schemes. Anyone who can reach the API can submit a review as any name.
7. **Review immutability is app-level only (P2).** The FK is `ondelete="RESTRICT"` (`models/sar_candidate.py:129-130`), and the model docstring says "application-enforced append-only" (`:121-122`), but there is no database trigger preventing `UPDATE` or `DELETE`. The guarantee is only as strong as the service code.
8. **Fusion can prefill the analyst decision (P0/P1).** The "Adopt Recommendation & Populate Notes" button maps `MULTI_SENSOR_CONCORDANCE` → `potential_oil_slick`, `BIOGENIC_LOOKALIKE` → `rejected_lookalike`, etc. (`CandidateReview.tsx:602-619`). This converts a rule-based synthesis into the analyst's recorded decision with one click, creating automation bias in the audit trail.
9. **Stale UI caption (P2).** `CandidateReview.tsx:1108` says "203 awaiting + 4 reviewed = 207 eligible". Live API says **202 awaiting + 5 reviewed = 207**. The composition is stale even though the total happens to match.
10. **KPI reconciliation gap (P2).** API `standard_review_candidates=136`; raw DB `screening_status='candidate_requires_review'` count is **137**. The API likely applies an additional wind-range filter; this is undocumented and untested. Reconcile the definitions.

**Scientific assessment**

The candidate rows are a frozen replay of a research audit CSV, not live inference. That is a legitimate design for a review demo, but it must be labelled as such. The blinding claim is false because `split` and `safe_scene` are exposed. The benchmark isolation test itself fails, which means the project's own test suite no longer supports the "held-out" claim.

**Status: Partial. Plumbing works; scientific integrity does not.**

### 5.4 Full-scene SAR — fabricated detections, no raster input

**What exists**

- `backend/app/vision/sar_scene_processor.py` claims full-scene Sentinel-1 processing, overlapping-window tiled inference, Hanning blending, GeoJSON footprints and probability heatmaps.
- `backend/app/services/sar_scene_service.py` lists 148 scenes and lazily processes them.

**What the code actually does**

`process_scene()` never opens a raster. It:

1. Takes a default `scene_raster_shape=(1536, 1536)` (`:139`).
2. Creates `rng = np.random.default_rng(seed=hash(scene_id))` (`:181`).
3. Draws `num_candidates = rng.integers(3, 7)` (`:189`).
4. Injects "synthetic ocean backscatter background" and "3-6 candidate dark formations" (`:183-196`).
5. For each tile near a simulated center, assigns `p_oil = clip(0.70 + ... + rng.normal(...), 0.50, 0.98)` and random dB values (`:214-229`).
6. Writes `candidate_footprints.geojson`, `probability_heatmap.png` and `metadata.json` (`:147-150`).

There is no Sentinel-1 SAFE/GRD read, no calibration, no speckle filtering, no real tile extraction, no model inference. The docstring's claim of "strict scientific distinction" is contradicted by the code.

**Runtime evidence**

- `GET /api/v1/sar-scenes?limit=1` returned `total=148`, first scene `is_processed=true`, `candidate_count=14`.
- A footprint GET for `S1B_IW_GRDH_1SDV_20190412T035040_20190412T035105_015768_01D985_9F88` returned **10 features** from **64 tiles**, `generated_at=2026-11-15T10:00:06Z`.
- The GET wrote new files under `backend/data/objects/evidence/sar_scenes/...` at 2026-11-15 15:30 local. The same scene already had separate files under root `data/objects/evidence/sar_scenes/...` from 2026-11-12. Two divergent copies now exist.

**GET side effect**

### 5.7 AIS vessels — seeded fleet, engineered associations, mislabelled method

**What exists**

- `backend/app/demo/seed_vessels.py` contains 6 hardcoded vessels with MMSI/IMO/name/type/flag.
- `backend/app/vision/ais_associator.py` interpolates tracks, gates by distance/time, scores associations, and marks a primary suspect.
- `backend/app/services/vessel_service.py` exposes vessel list/detail and candidate associations.

**What is real**

- The API and UI plumbing works: 6 vessels, 28 positions, 4 associations, 2 candidates with associations.
- The vessel detail endpoint returns 7 pings for Chem Polaris.

**What is fabricated**

`seed_vessels_and_tracks()` explicitly queries two candidates and generates tracks around them:

- `c_s1_36 = ... cand_s1_0036` (`:103`)
- `c_std_1 = ... cand_test_standard_001` (`:104`)
- MT Starlight pings are generated at `base_lat + h*0.015 + 0.035` and `base_lon + h*0.20`, with the comment "CPA ~4 km north" (`:108-137`).
- Chem Polaris pings are generated around the test candidate with "~6 km CPA" (`:163-191`).
- After inserting, the code **immediately triggers correlation** (`:221-226`).

So the "discovery" is constructed: the vessel is placed near the candidate, then the engine reports that the vessel is near the candidate.

**Scoring is not Bayesian**

The score is:

```python
dist_factor = exp(-(best_dist ** 2) / (2 * 15.0 ** 2))
time_factor = exp(-abs(best_offset_min) / 120.0)
raw_score = dist_factor * time_factor * (v_type_weight / 1.40)
final_score = clip(raw_score, 0.05, 0.99)
```

(`ais_associator.py:175-188`)

There is no prior, no likelihood, no posterior, no uncertainty. The module docstring and project docs call it "Bayesian suspicion scoring"; that is false.

**"CPA" is not a true CPA**

The code takes the minimum distance to a **ping**, or to an interpolated point only when the exact candidate time falls between two pings (`:148-169`). It does not project the candidate point onto the track segment to compute the closest point of approach. When interpolation is used, `best_offset_min` is set to `0.0` (`:167`), which forces the time factor to 1.0 and inflates the score. The UI then labels the result "CPA".

**Association output**

- `cand_s1_0036` → MT Starlight, 3.89 km, score **0.967**, `SOURCE_SUSPECT`, `is_primary_suspect=true`.
- `cand_test_standard_001` → Chem Polaris, 5.04 km, score **0.99**, `SOURCE_SUSPECT`, `is_primary_suspect=true`.
- Only **2 of 306** candidates have any association; 304 have none.

The primary-suspect flag is set whenever the top score is ≥ 0.55 (`:221-224`). There is no requirement that the vessel be a plausible source, no dark-transponder gap analysis, no MMSI/IMO validation, and no evidence beyond proximity.

**Scientific assessment**

A seeded track that is deliberately placed next to a slick, then scored by a proximity heuristic, is not vessel attribution. Calling the result "Primary Suspect" and 99% is an operational allegation. It must be removed or explicitly labelled as a synthetic demonstration.

**Status: Broken / misleading.**

### 5.8 Lagrangian drift — constant forcing, random beaching, invalid stored mass balance

**What exists**

- `backend/app/vision/lagrangian_drift.py` implements particle advection, wind leeway, Stokes drift, Coriolis deflection, Langevin diffusion, weathering, beaching and mass-balance timelines.
- `backend/app/services/drift_service.py` persists simulations and exposes candidate drift.

**What is real**

- The numerical engine executes.
- A new 48-hour simulation (`sim_53e90590af26`) ends at 100.0% total mass: 30.9% evaporated + 69.1% floating + 0.0% beached + 0.0% dispersed.
- GeoJSON trajectory and hourly timeline are produced.

**What is wrong**

1. **Constant forcing.** `simulate()` defaults to `current_speed_ms=0.22`, `current_direction_deg=90.0` (`:145-146`). There is no CMEMS client, no bathymetry, no coastline, no tidal current, no spatial variability. `grep` for CMEMS finds only docs and schema defaults; `copernicusmarine` is not installed.
2. **Random beaching.** The beaching condition is:
   ```python
   if is_coastal and h >= 6 and (rng.uniform(0, 1) < 0.04 * (h / 12.0)):
   ```
   (`:244`). It depends only on the `is_coastal` boolean and a random draw. `dist_from_origin` is computed at `:238-241` but never used. A particle can "beach" while moving away from shore, and an offshore particle can never beach regardless of geography.
3. **Mass balance can exceed 100% in stored data.** The legacy row `sim_aeb146835dbc` (candidate `cand_test_standard_001`) has:
   - evaporated 31.0%
   - floating **0.0%**
   - beached **99.3%**
   - dispersed 0.4%
   - **sum 130.7%**
   The code computes `floating_pct = max(0.0, 100.0 - evaporated - dispersed - beached)` (`:275-279`), which clamps floating to zero but does not renormalise the other components. The stored JSON preserves the invalid sum. The UI reports `beaching_risk_level="CRITICAL"` from this row.
4. **The new row hides the bug.** `sim_53e90590af26` sums to 100.0% because floating was positive. This does not prove conservation; the clamp still permits >100% whenever beached + evaporated + dispersed exceed 100.
5. **GET auto-runs a simulation.** `get_candidate_drift_simulation()` returns the latest row or creates a new 48-hour simulation (`drift_service.py:162-179`). During the audit, a GET inserted `sim_53e90590af26`.

**Scientific assessment**

This is a particle animation, not an oil-spill forecast. Constant currents and random beaching cannot support trajectory, arrival-time, or beaching-risk claims. The mass-balance defect is a concrete correctness bug, not just a modelling limitation.

**Status: Partial / misleading.**

### 6.1 Ground-truth leakage (P0)

**Where**

- API: `SARCandidateOut.split` and `.safe_scene` (`schemas/candidate.py:20-22`).
- Route: list/detail responses (`candidates.py:110-119`, `:169-175`).

**Why it matters**

The project claims "Data-Blindness & Review Integrity" and a "leakage-free" benchmark. A reviewer can see which split a candidate belongs to and can filter the queue by split. That is sufficient to bias decisions and to invalidate any held-out evaluation performed through this interface.

Remove `split`, `safe_scene`, `cluster`, `subset`, `ground_truth` and internal sample IDs from every public schema/response. ### 6.2 Simulation/observation conflation (P0)

**Where**

Treat every "Fully Verified" label as unproven until it links to a reproducible test or a runtime evidence record. Replace the counts with the actual suite output. Add a "Verification status" column that distinguishes `IMPLEMENTED`, `RUNS`, `VALIDATED`, `SIMULATED`, `BLOCKED`.

### 6.7 Authentication and authorization (P2)

- OpenAPI `components.securitySchemes` is empty.
- The review endpoint accepts `reviewer_id` from the request body, default `"analyst_local"` (`schemas/candidate.py:97-100`).
- No route checks a role or identity.
- The UI discloses "local-development attribution", but the API does not enforce it.

**Impact:** Any client that can reach the API can submit, overwrite the appearance of, or attribute a review to any name. The audit trail is not attributable.

**Fix:** Add authentication for write routes; derive reviewer identity from the authenticated principal; keep a local-development bypass only behind an explicit env flag and a visible banner. Add authorization tests for review submission and evaluation triggers.

### 6.8 Review immutability (P2)

The model docstring says "application-enforced append-only" (`models/sar_candidate.py:121-122`). The FK is `RESTRICT` (`:129-130`), which prevents deleting a candidate that has reviews, but there is no trigger or rule preventing `UPDATE`/`DELETE` on `sar_candidate_reviews`. A direct SQL client can rewrite history.

**Fix:** Add a database trigger that rejects `UPDATE` and `DELETE` on the review table (or a signed hash chain if regulatory-grade immutability is required). Keep the application-level guard as defence in depth.

### 6.10 Database integrity (pass)

Observed:

### 6.11 Encoding (P3)

Mojibake appears in source docstrings and some stored/displayed strings, e.g., `0.25A�` in `era5_client.py` and `A�` in water text. This is a UTF-8/Windows-1252 round-trip issue. It does not break functionality but undermines a data product whose value proposition is trustworthy provenance.

**Fix:** Normalise source and data to UTF-8, add a CI check for the replacement character (`U+FFFD`), and repair affected stored strings with an additive data migration.

**Fix:** Consolidate path configuration, add the real runtime dependencies to the manifest (or make vision imports lazy/optional), and remove or implement the phantom endpoints.

## 8. Scientific validity assessment

### 8.1 What can be claimed today

- The water-quality archive contains 4,601,153 observations for 2,740 water bodies and 4,951 stations.
- The water Q&A is grounded in stored records and returns citations without an LLM.
- The SAR candidate table is a faithful replay of a research audit CSV containing 300 rows across four research splits.
- The SAR candidate confidence is explicitly uncalibrated.
- The optical **scene metadata** (granule, platform, tile, acquisition time, cloud cover) is real.
- The database schema and referential integrity are sound.
- The application runs locally and serves a coherent UI.

### 8.2 What cannot be claimed today

- That the candidate review is blind. It is not.
- That the benchmark is leakage-free. The leak is exposed and the isolation test fails.
- That full-scene SAR detections are real. They are random formations.
- That optical BOA/NDCI/SCL metrics are measured. They are generated.
- That fusion provides a calibrated "high probability" of oil. It is a constant over simulated inputs.
- That AIS identifies a vessel. The tracks are seeded and the score is a proximity heuristic.
- That drift predicts beaching. The forcing is constant and beaching is random.
- That environmental impact is assessed. It is a distance lookup against 9 points.
- That any of the above is "Fully Verified".
- That the system is operational or suitable for regulatory/response decisions.

### 8.3 Corrected language for the current state

| Current copy | Honest replacement |
|---|---|
| "High probability petroleum slick" | "Rule-based concordance flag; inputs include simulated optical data; not a probability" |
| "Primary Suspect" | "Nearest seeded vessel in a synthetic demonstration" |

| "Bayesian suspicion score" | "Heuristic proximity score" |
| "Sentinel-1 SAR Scene detections" | "Synthetic demonstration footprints" |

### 8.4 Validation gaps

- No labelled ground-truth set is present in the operational database.
- No precision/recall/calibration metrics exist for the deployed SAR v1 or the mock detector.
- No held-out evaluation can be trusted while `split` is exposed.
- No external validation of drift, AIS, or impact outputs.
- No uncertainty quantification anywhere in the marine chain.
- No provenance record distinguishes measured, modelled, and simulated layers.

## 10. Prioritized remediation roadmap

> **Do not start Phase 19 until this audit is accepted and the priorities below are agreed.** The ordering is intentional: integrity first, real data second, models third, operations last. Adding features before P0 fixes would compound the provenance problem.

### Phase 19 — Integrity gate (P0 + P1-07)

**Goal:** Make the system honest about what it knows, and make reads safe.

**Tasks**

1. Remove `split`, `safe_scene`, `cluster`, `subset`, `ground_truth` and internal sample IDs from all public schemas and responses. Keep them in an internal-only provenance table/endpoint with explicit authorization.
2. Remove the corresponding fields and "(Research Benchmark)" copy from `CandidateReview.tsx`; replace with neutral candidate metadata.
3. Add a mandatory provenance envelope to every response:
   - `data_origin`: `OBSERVED | DERIVED | MODEL | SIMULATION | RECOMMENDATION`
   - `is_simulated`: boolean, computed from records
   - `generator`: engine/model/version
   - `generated_at`
   - `source`
4. Add a visible "SIMULATED" banner to any UI panel backed by synthetic SAR, optical, AIS, drift or impact data.
5. Remove "High probability petroleum slick", "Primary Suspect", "CPA", "Bayesian" and "CRITICAL" from synthetic paths; use neutral, evidence-qualified language.
6. Convert every side-effecting GET to an explicit POST job. GETs return existing results or `404/409`.
7. Add `is_fixture`/`dataset_role` to candidates; exclude fixtures from operational views and KPIs; mark demo reviews and exclude them from "reviewed" counts.
8. Remove the one-click "Adopt Recommendation & Populate Notes" behaviour; require an independent analyst decision and record any advisory input separately.
9. Fix `DATA_ROOT` resolution; add startup assertions; remove duplicate `backend/data` after migrating unique files.
10. Correct the test counts and "Fully Verified" claims in README, LOCAL_DEVELOPMENT, IMPLEMENTATION_STATUS and the completeness matrix. Link claims to evidence.

**Acceptance criteria**

- A contract test asserts that no `/api/v1/sar-candidates*` payload contains `split`, `safe_scene`, `cluster`, `subset` or `ground_truth`.
- A GET-purity test snapshots row counts and file mtimes before/after every GET and asserts no change.
- `contains_simulated_data` is true for every payload containing synthetic layers.
- Operational KPIs exclude the 6 fixtures and 8 demo reviews.
- 645 tests pass from both repo root and `backend/`.
- No page displays "Research Benchmark", "Primary Suspect" or "High probability petroleum slick" on synthetic data.
- Documentation contains no unqualified "Fully Verified" claim.

### Phase 20 — Real data paths (P1-01, P1-02, P1-09)

**Goal:** Replace fabricated pixels with real Earth-observation reads, or fail honestly.

**Tasks**

1. Implement real Sentinel-1 GRD/SAFE access (CDSE or local archive), calibration, tiling and model inference. Remove RNG formation injection from the production path.
2. If no raster is available, return `DATA_UNAVAILABLE` with a reason; never generate synthetic footprints in non-demo mode.

4. Render true-colour, false-colour, SCL and NDCI products from real arrays; persist under `DATA_ROOT`.
5. Fix candidate and optical image serving; add 200/content-type tests.
6. Declare `numpy`, `Pillow`, `requests` (and `rasterio` if adopted) in `requirements.txt`; add a clean-install CI job.
7. Add a per-scene/per-candidate data-availability badge in the UI.

**Acceptance criteria**

- Processing two different real scenes produces different footprints driven by raster content; no RNG in the production path.
- Optical metrics change with the input pixels; images return 200 with correct content type.
- A missing raster produces `DATA_UNAVAILABLE`, not synthetic output.
- A clean venv from `requirements.txt` starts the app and imports all routes.
- Tests pass from the documented working directory.

### Phase 21 — Scientific models (P1-03 … P1-06, P1-08)

**Goal:** Replace placeholders with validated models, or clearly label them as demonstrators.

**Tasks**

1. **AIS:** ingest real AIS (or keep a clearly labelled demo); validate MMSI/IMO; implement true CPA by projecting onto the track segment; add uncertainty; remove the Bayesian claim; require positive evidence before any "suspect" label.
2. **Drift:** ingest CMEMS currents, bathymetry and coastline; remove random beaching; conserve mass exactly across all rows; add skill/uncertainty; version the forcing dataset.
3. **Impact:** replace the 9 hardcoded points with PostGIS receptor geometries (MPA boundaries, coastline, intakes); compute distance-to-geometry; publish the vulnerability formula; handle zero receptors explicitly.
4. **Fusion:** calibrate thresholds against labelled data; remove the hardcoded 0.92; output a score with uncertainty and a clear "not a probability" label until calibrated.
5. **Detectors:** publish precision/recall/calibration for any model described as deployed; make model selection explicit; label mock clearly.
6. **Validation:** create a leakage-controlled held-out evaluation; report metrics and failure modes; no "validated" claim without evidence.

**Acceptance criteria**

- AIS association uses a true CPA and a documented score; no "Primary Suspect" without positive evidence.
- Drift mass balance passes a conservation test for every stored row; forcing provenance is recorded; no random beaching.
- Impact uses PostGIS geometries and returns zero-with-explanation when no receptor is nearby.
- Fusion has a calibration report or is explicitly labelled uncalibrated.
- Model registry shows real metrics or explicit "not evaluated".

## Appendix D — Audit conclusion

The repository contains real engineering value: a substantial water-quality archive, a deterministic retrieval system, a clean PostGIS schema, a working review UI, and a broad, coherent frontend. Those assets deserve to be preserved and built upon.

The marine intelligence chain, however, is currently a demonstrator whose newest layers generate the appearance of evidence rather than evidence. The most urgent work is not more modelling; it is restoring the truth boundary between what was measured, what was modelled, what was simulated, and what is a recommendation. Until that boundary is enforced in schemas, provenance, UI copy, and tests, adding capability will make the system less trustworthy, not more.

**Recommended next action:** accept or amend this audit, then authorize Phase 19 (Integrity gate) only. Do not begin Phase 20–22 work, model retraining, or deployment until Phase 19 acceptance criteria pass.
