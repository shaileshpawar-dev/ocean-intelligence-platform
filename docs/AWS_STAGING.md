# AWS staging

**Nothing in this document is deployed.** The template
([`infra/aws/staging.yaml`](../infra/aws/staging.yaml)) and the scripts
([`aws_staging_deploy.sh`](../scripts/aws_staging_deploy.sh),
[`aws_staging_teardown.sh`](../scripts/aws_staging_teardown.sh)) are written,
reviewed and costed; no AWS resource they describe exists in the account. The
decision was to deliver the infrastructure and the runbook without the
standing charge. Everything below is therefore a design statement or a price,
never a measurement — the measured numbers in
[IMPLEMENTATION_SUMMARY.md](../IMPLEMENTATION_SUMMARY.md) come from the local
production-like stack.

## Shape

```
Internet
   │  HTTP :80
   ▼
Application Load Balancer          health check: /api/v1/health/ready
   │  :8000, ALB security group only
   ▼
ECS Fargate service (1 task)       ENVIRONMENT=staging
   │  :5432, service security group only     WATER_BOOTSTRAP_STATES=""
   ▼
RDS PostgreSQL 16.4 + PostGIS      not publicly accessible
```

and, entirely separately:

```
EventBridge Scheduler ──▶ ECS RunTask (job task definition) ──▶ RDS
                                     │
                                     └──▶ S3 (evidence objects)
```

The web service never ingests. Every expensive thing — ingestion, geometry,
satellite processing, RAG reindex — is a one-off task with the same image and
a different command.

## Why there is no NAT gateway

Tasks run in public subnets with `AssignPublicIp: ENABLED`, which is how the
account's existing services are built. A NAT gateway costs about **$33/month**
— more than the database — and would buy an egress path the security group
already controls: nothing may reach a task except the load balancer, and the
database accepts connections only from the service's security group. The
trade-off is explicit rather than conventional.

## Security groups

| Group | Inbound | From |
|---|---|---|
| `AlbSecurityGroup` | 80 | `0.0.0.0/0` — the only public ingress |
| `ServiceSecurityGroup` | 8000 | the ALB security group |
| `DatabaseSecurityGroup` | 5432 | the service security group |

`0.0.0.0/0` appears once, on the load balancer. PostgreSQL is never exposed;
`PubliclyAccessible: false`.

## IAM

Three roles, none administrative:

- **execution role** — the AWS-managed `AmazonECSTaskExecutionRolePolicy`
  (pull the image, write logs) plus `secretsmanager:GetSecretValue` on the one
  database secret;
- **task role** — `s3:GetObject/PutObject/DeleteObject` on
  `arn:…:oceanai-water-staging-evidence-<account>/*` and `s3:ListBucket` on
  that bucket. Nothing else in AWS;
- **scheduler role** — `ecs:RunTask` on the job task definition and
  `iam:PassRole` on the two roles above.

The deploying credential (`synq-deployer`) currently holds **PowerUserAccess
and IAMFullAccess** through the `SYNQ-Deployers` group. That is far more than
a deploy needs and is shared with the account's other projects; narrowing it
is a recommendation, not something to change unilaterally, because it would
affect those projects too.

## Secrets

The database password is generated by CloudFormation into Secrets Manager and
injected as a task **secret**. It is not in the template, the repository, the
task environment, or any script output. `DATABASE_URL` is assembled inside the
container from `$PGUSER`/`$PGPASSWORD` so the password never becomes a
console-visible value.

The previously exposed ngrok token and GCP service-account key **must remain
revoked and rotated**. No replacement is committed anywhere, and none should
be.

## S3

The database holds metadata — scene id, sensor, acquisition date, footprint,
cover fractions, the derived index, provenance — and S3 holds objects. No
image bytes go into PostgreSQL. The bucket blocks all public access, is
encrypted (AES256), is versioned with a 30-day expiry on old versions, and its
policy denies any non-TLS request. It is `Retain` on stack deletion: satellite
scenes cost real processing, and tearing down staging is not a reason to lose
them.

Today the platform stores scene metadata plus the imagery service's URL, which
is why staging can run with the bucket empty; moving the rendered chips into
S3 is a code change (`WATER_EVIDENCE_BUCKET` is already passed to both task
definitions) and is listed as remaining work.

## Migrations

The order is **backup → migrate → verify → deploy**, and the template supports
it:

1. RDS automated backups run daily with 7-day retention, and the stack's
   `DeletionPolicy: Snapshot` means a final snapshot survives teardown.
2. `db upgrade` runs as its own task, before anything serves. It is never run
   by the web container: `init_db()` on a server database creates nothing and
   only checks that `alembic_version` exists.
3. A task that starts against an unmigrated database stays alive and answers
   `/api/v1/health/ready` with **503 `schema_not_migrated`**, so the load
   balancer keeps it out of rotation rather than serving errors. The probe
   re-checks every 60 seconds, so the task joins rotation on its own once the
   migration lands.
4. No migration in this project drops a column or a table holding data. The
   one destructive-looking step — the geometry re-derivation — rebuilds a
   derived column from the stored GeoJSON, which is the provenance copy.

Restore: `aws rds restore-db-instance-from-db-snapshot`, point
`PGHOST` at the new endpoint, redeploy. Restoring has not been rehearsed —
doing so needs an isolated environment, and there is none.

## Cost

Prices from the AWS Pricing API for `ap-south-1` on 26 September 2026,
on-demand, 730 hours:

| Item | Rate | Monthly |
|---|---|---|
| Application Load Balancer | $0.0239/hr | $17.45 |
| ALB capacity units | $0.008/LCU-hr | up to ~$5.84 at 1 LCU; staging traffic is far below |
| Fargate 0.25 vCPU + 0.5 GB (x86) | $0.04256/vCPU-hr, $0.004655/GB-hr | $9.47 |
| RDS `db.t4g.micro` PostgreSQL, Single-AZ | $0.021/hr | $15.33 |
| RDS gp3 storage, 20 GB | $0.131/GB-mo | $2.62 |
| CloudWatch Logs (7-day retention) | — | ~$1 |
| S3, EventBridge schedules | $0.025/GB-mo, free | <$0.10 |
| **Total** | | **≈ $46/month** |

Two levers, both real:

- **Graviton.** Fargate ARM is $0.02383/vCPU-hr and $0.00261/GB-hr — the task
  drops from $9.47 to **$5.30**. It needs an `arm64` image build.
- **Drop the ALB** and give the task a public IP: **−$17.45/month**, at the
  cost of a stable hostname and a TLS termination point.

The jobs add Fargate seconds only while they run: the hourly real-time sync is
about 30 seconds of a 0.5 vCPU task, roughly $0.30/month.

## Schedules

Cadence follows the source, not a convention:

| Job | When | Why |
|---|---|---|
| `sync-water-data --provider cpcb_rtwqms --all` | hourly | the analysers publish hourly |
| `sync-water-data` for `cpcb_nwdp` and `cwc_nwdp` | weekly, Sunday | monthly extracts at most; an unchanged resource costs one request |
| `process-satellite --limit 80` | weekly, Saturday | Sentinel-2 revisits every five days and most passes are rejected for cloud |

A failed job leaves the previous data untouched and records the failure
(`ingestion_runs`, visible at `GET /api/v1/water-jobs`).

## Observability

CloudWatch Logs holds structured JSON from both task families, 7-day
retention. What to watch, in order of usefulness:

- `GET /api/v1/water-jobs` — when each kind of job last succeeded. This is the
  question that matters for a scheduled system;
- ALB target health — driven by `/health/ready`, so it goes unhealthy for a
  database outage or an unmigrated schema;
- log events `job_failed`, `ingest_planning_failed`, `provider_unavailable`;
- RDS `FreeStorageSpace` and `CPUUtilization` (a `t4g.micro` has 1 GB of RAM;
  the heaviest water-body page is the thing most likely to feel it).

## Runbook

```bash
export VPC_ID=vpc-...            # a VPC with two public subnets, different AZs
export SUBNET_IDS=subnet-a,subnet-b
bash scripts/aws_staging_deploy.sh
```

The script builds and pushes the image, deploys the stack, then runs migrate,
seed, the real-time sync and the boundary import as separate tasks, and
finally polls `/health/ready`. Tear down with
`bash scripts/aws_staging_teardown.sh` — it scales the service to zero,
deletes the stack, keeps the final RDS snapshot and the evidence bucket, and
names both.

## What deploying would still not prove

Honest gaps, so the eventual first deploy is not a surprise:

- outbound access from inside the VPC to `nwdp.nwic.gov.in`,
  `rtwqmsdb1.cpcb.gov.in`, the Geofabrik mirror and Microsoft Planetary
  Computer is **unverified** — local connectivity is not AWS connectivity;
- `db.t4g.micro` against the full 4.6M-observation dataset is untested; the
  Ganga page takes 654 ms on the development machine and that machine has
  more memory than the instance;
- the geometry job needs the 1.7 GB OSM extract, which has no home in this
  design yet (S3 plus a download step, or a larger ephemeral volume);
- no TLS certificate, so the listener is HTTP; ACM plus a hostname is the
  remaining step before anyone else should use the URL.
